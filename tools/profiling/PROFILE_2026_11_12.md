# Nodus table and row timing, 2026-11-12

## Setup and scope

Windows Release build, `NODUS_ENABLE_TORCH=OFF`, Ryzen 9 7900X (12 cores,
24 logical processors). Each of 112 configurations ran for 0.5 seconds in
three separate processes. Figures below are medians of the three runs.
The harness uses real GraphRuntime tool rows, ThreadManager contracts, the
existing typed stack, and connected table-edge FIFOs. Value and FIFO order
assertions passed in every case. The previous checked-stack baseline was
branch commit `336751c` plus the same nanosecond timing fix used in the new
build. The scalar-path build adds the declared-contract stack optimization.

The profiled job categories are independent plugin rows (0 to 5000 us of
work), single builtin Add/Multiply/Divide/Modulo rows, 64-Add chains in
1/2/4/8 tables, connected producer/consumer pipelines, and four-producer
fan-in. These cover table scheduling, tool stack operations, input/output
contacts, and FIFO handoff. This is not an inventory of every plugin or GPU
row type. Timing is per table module, so a single-math case includes its
plugin source and sink. It cannot isolate an individual row's exact time.

## Measured throughput

| Case | Mode | Checked stack | Declared scalar stack | Scalar module wall time |
|---|---|---:|---:|---:|
| Single Add table | Free | 3.57M/s | 4.14M/s | 0.15 us |
| Single Multiply table | Free | 3.53M/s | 3.94M/s | 0.16 us |
| Single Divide table | Free | 3.55M/s | 4.17M/s | 0.15 us |
| Single Modulo table | Free | 3.50M/s | 4.13M/s | 0.15 us |
| One 64-Add table | Free | 147k/s | 210k/s | 4.40 us |
| Eight independent 64-Add tables, combined | Free | 22.8k/s | 101k/s | 78.3 us/table |
| Eight independent 64-Add tables, combined | Pooled | 22.9k/s | 77.6k/s | 43.2 us/table |
| Two-table FIFO pipeline, no work | Free | 1.75M delivered/s | 1.71M delivered/s | 0.22 us consumer |
| Two-table FIFO pipeline, 100 us consumer | Free | 9,958 delivered/s | 9,933 delivered/s | 100.5 us consumer |
| Four-producer fan-in, 100 us consumer | Free | 9,832 delivered/s | 9,844 delivered/s | 101.1 us consumer |

The math chain improvement follows the removal of a global type-registry
lock and byte-by-byte type-mask scan for each builtin stack push/pop in a
module declared `ScalarF32` with the existing Float64 backing type. The
declared type ID is now resolved once; the data path still checks capacity,
underflow, and backend-copy success. `Opaque` and other mixed contracts keep
the checked typed-stack behavior. The existing plugin stack helpers also
remain checked. A same-size wrong-type pop is tested and rejected there.

Independent work shows the scheduler boundary. With eight independent
100-us plugin rows, Free completed about 79.1k modules/s, Pooled about
52k/s, and Sequential about 8.4k/s. With 1-ms work, Free completed about
8k/s, Pooled about 7.5k/s, and Sequential about 980/s. At 100-us work in
a two-table FIFO pipeline, Free delivered about 9.9k/s, while Pooled and
Sequential delivered about 7.8k/s and 7.6k/s. These are aggregate rates,
not per-worker rates.

The direct `ValueTypeRegistry::get` diagnostic fell from about 132M calls/s
with one thread to about 18M total calls/s with eight and 9.9M total calls/s
with sixteen. This demonstrates shared-lock contention, but the remaining
eight-table math slowdown cannot be assigned to that lock alone. In the
new scalar run, one 64-Add module takes about 4.4 us; eight parallel tables
take about 78 us/module. Stack backend copies, plugin source/sink calls,
ThreadManager bookkeeping, and system scheduling remain possible costs.

Free-mode stop latency was variable and can reach tens of milliseconds for
independent work (median roughly 35 ms for eight 100-us rows). That follows
the current adaptive worker batch, whose upper bound is 50 ms. It is a
shutdown/control latency issue, not per-row execution time.

## Evidence and limits

The committed aggregate data are in `results/checked_stack_summary.json`,
`results/scalar_stack_summary.json`, `results/math_scaling.csv`, and
`results/type_registry_scaling.csv`. The raw per-module CSVs are in the
user-space profile output directory. The recipe and optional CMake targets
are in this folder's README. Three ThreadManager tests and the frame
serialization/type-mismatch test pass on the final source.
